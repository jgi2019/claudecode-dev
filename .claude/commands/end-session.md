## 役割分担ルール（重複回避 = 「どっちに渡したっけ」問題の解）
記事ドラフトの担当を出自で分ける。同一トピックの二重ドラフトを防ぐ:
- **JIRO（実行ログ視点）** = Base44・実装・デバッグ・インフラ・MCP構築など「手を動かした」セッション。バイブコーディング体験記の生素材はここで生まれる
- **TARO（戦略ログ視点）** = 壁打ち・事業設計・市場整理など「考えた」セッション
- 書く前に **記事DBを同トピックで検索**。既存ドラフトがあれば新規作成せず追記 or スキップし、備考に出自（JIRO実行ログ）を明記

## ① チャットハンドオフ
- 出力先: ハンドオフDB `collection://27e1a509-0fb5-4a07-824e-799985d70a3f`
- トピック別にエントリ作成（1トピック1エントリ）

### 必須フィールド
- タイトル: トピック要約（何を議論し、何が決まったか）
- v: 同トピックの連番（初回は1）
- ステータス: 🟡着手待ち / 🔵進行中 / 🟢引き継ぎ済み
- トラック: 🔧インフラ / 🛠️アプリ開発 / 📣ブランディング / 🎯流入・案件 / 📝コンテンツ / 🤝パートナー
- プロジェクト: AIオンボーディング / Base44 / AI Worker Pass / JIRO/ソロプレナーOS / Meishift / クライアント / その他
- 作成日: 今日の日付
- 次アクション: 具体的に（「〇〇を△△してから□□に着手」）

### ページ本文の構造
```
# [トピック名] - [日付]
## 決まったこと
## 議論の経緯（割愛しすぎない。判断理由・ニュアンスを残す）
## 未解決・保留事項
## 関連NotionページURL
```

### AIOS v0.2本文（上記Markdownの前に置く）
- `.claude/templates/aios-handoff-v0.2.yaml` の全フィールドを本文冒頭へ置く。既存DBのselect値は変更・追加しない。
- `project_id` はPJレジストリ行のpage ID。親ページIDやDB IDで代用しない。
- `execution.status`: `succeeded / partial / failed / unknown`。**今回の `approval.scope` 内の必須ステップ**で判定する。
  - 許可範囲内の全必須ステップを検証済みなら `succeeded`。基盤全体の将来課題は `open_questions` に残し、この操作を `partial` にしない。
  - 許可範囲内に未完が残れば `partial`。目的を達成できず成功成果物もなければ `failed`。外部結果を照合できず再実行すべきでなければ `unknown`。
- `failed_steps` は今回の許可範囲内にある現在の未完、`attempt_log` は過去の試行履歴、`notification_receipts` は送信成功の受領証を置く。
- 模擬出力は `simulation: true` とし、実行・承認の事実と混ぜない。
- 保存後にページを再取得し、必須キー・値・URLが一致した成果物だけを `verified: true` とする。

### 発動判定

### 記事DBプロパティ
- タイトル: 記事タイトル案
- 著者: **JIRO**（TARO=戦略ログ視点 / JIRO=実行ログ視点。重複回避はこの著者欄で判別）
- ステータス: 📝下書き
- シリーズ: AIオンボーディング / B44-JA / AdOpt / 名刺管理ツール / インテントサーチ / Builder's Ops から該当を選択
- ソースPJ: 対応するハンドオフページURL（①で作ったもの）
- チャットURL: JIROはN/A。ハンドオフURL or 該当git commit URLを入れる
- 画像保管庫（GoogleDrive）: 画像を使う場合のみDriveフォルダURL
- 備考: セッション日付・要点メモ

### トーン
執筆スタイルガイド準拠（バイブコーディング肯定、ハマりは事件・謎解き、ツッコミ先はClaude）。
JIRO視点なので**実行ログを芯に**: 差分・コマンド・パス・commit hash・✅検証結果・再現手順。

### 画像の付随処理（Code版 / ファイル渡し前提）
**大前提**: JIROはクリップボード貼付画像を扱えない（ファイル化されない・Ghostty貼付は不安定）。
スクショは必ず**ファイル**で用意する。HEYの運用: Shottrで撮影→`~/Desktop/**screenshots` に自動保存＋クリップボードコピー。

1. スクショ元フォルダ `~/Desktop/**screenshots` の直近ファイル、およびセッション中にコミット/生成した画像の実ローカルパスを洗い出す
2. 記事本文に配置ガイドを記載（どの画像をどのセクションに / マスク対象は何か）
3. Drive「記事DB連動スクショ保管庫」(`0AJvfeB4ymDtsUk9PVA`) に記事タイトル同名フォルダを作成し、
   **JIROがMCP(Google Drive)で該当画像を自動アップ** → フォルダURLを記事プロパティ「画像保管庫（GoogleDrive）」に記入
   （TARO版のHEY手動アップは不要。JIROはファイルさえあれば一気通貫でアップできる）
4. base64大量送信は避ける。原則ローカルパス参照で扱う

## ④ TAROへの申し送り自動投稿（双方向バス）
Slack `#taro-jiro`（Channel ID: `C0BGKGN721X`）に、セッション終了時の申し送りを自動投稿する。

### 投稿内容（3点）
1. 今セッションの要約（成果・主要な変更）
2. TAROへの共有事項・質問（設計判断・戦略に関わるもの）
3. 未解決・引き継ぎ事項（次にどちらが何をやるか）

### フォーマット（統一）
- 冒頭を `:incoming_envelope: JIRO → TARO 申し送り（YYYY-MM-DD）` で始める
- 末尾に `— JIRO（Claude Code / Layer 2）`
- 洞察メモ等はセッション中でも随時投稿OK（HEYが「TAROに伝えて」と言った場合は即投稿）

### AIOS通知記録・復旧
- 通知本文に `[PJ:xxx]`、`operation_id`、結果（succeeded / partial / failed / unknown）、正本URL、未完事項と次ownerを含める。
- 送信成功後は `notification_receipts` に channel / message_id（Slack ts）/ permalink / operation_id / sent_at を記録する。
- 成果物保存済みで通知未達が確定した場合、保存をやり直さず同じ `operation_id` で通知だけ再試行する。
- 到達したか不明な場合は先に受信側を照合する。照合不能なら自動再送せず `unknown` として引き継ぐ。
- 全ステップ成功前に「完了」と書かない。
- 通知受領証をhandoffへ反映した後、**最終再実行判定**を行う。同じ `operation_id` の完成済み記録が1件あり、許可範囲内の必須ステップが揃っていれば追加書込みを省略する。これを最終状態のidempotency確認とする。

### 設計思想（なぜ二層か）
- **Notion = 正本ハブ**（重い文脈・決定・判断理由を割愛せず格納）＝ ①②
- **Slack #taro-jiro = 申し送りバス**（軽い非同期通知。"次これやって"だけ飛ばす）＝ ④
- 自動 = セッション終了時に漏れなく飛ぶ（忘れ防止）/ 手動 = リアルタイムで伝えたい時
- TARO↔JIRO 双方向。JIROは投稿、start-session で受信する

## 品質チェック（IMPORTANT）
書き出す前に自問:
- 次のセッションで「なぜこう決まったんだっけ？」が起きないか？
- 会話の重要なニュアンス・背景を飛ばしていないか？
- 次アクションが「検討する」のような曖昧表現になっていないか？
- ②を作った場合、TARO側に同トピックの既存ドラフトが無いか確認したか？
- 次のAgentが、正本の版・許可範囲・未完ステップ・再開地点を会話履歴なしで判断できるか？
- 予定・提案・模擬と、検証済みの実行事実を混同していないか？
- `status` は今回の許可範囲で判定したか？ 基盤全体の未実装事項だけを理由に `partial` にしていないか？
- 通知受領証の反映後に最終再実行判定を行い、追加書込みがないことを確認したか？
- 通知の送信要求成功だけで、受信側への到達を断定していないか？
- 秘密情報・個人情報をhandoffやSlackへ含めていないか？
